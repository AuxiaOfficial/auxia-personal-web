## 0. 三句话结论

1. **不是思考深度的问题，是深度的投入方向错了**：在需求还没冻结的时候，就进入了实现细节的深挖。
2. **"2 小时/轮"这个前提需要修正**：按实测时间线，六轮合计约 8 小时（12:58 → 21:00），平均约 80 分钟/轮，
   且这 8 小时里包含"从零搭一个站 + 建立 259 条自检"。单轮 2 小时的情况出现在**一轮塞了 9 项主任务 + 3 项次要任务**的那种轮次。
3. **AI 确实做了无用功，但它可以归类、可以量化、也可以基本归零**：日志里记录的问题条目约 23 条，
   其中约 12 条是真代码缺陷（必须修，属正常成本），约 11 条是环境坑、测量返工与自我假绿（这类本该为 0）。

**六轮 ≈ 8 小时，平均 ≈ 80 分钟/轮。**

### 1.2 每轮的固定成本在增长

自检条数：80 → 128 → 160/167 → 209 → 255 → 259。

每一条都是"这轮新出现的坑，补一条守卫防复发"。方向是对的，但意味着**每轮的收尾成本随项目年龄线性上升**——
第 1 轮收尾只要跑 80 条，第 6 轮要跑 259 条再逐条注入故障验红。这部分不是浪费，但必须被计入预算。

`dist/` 规模：143 文件/8.8MB → 138/7.54MB → 139/7.62MB → 141/8.1MB（体积稳定，说明没有失控膨胀）。

### 1.3 最反直觉的一条：机械步骤其实很快

实测（文件 mtime + 线上响应）：

- `index.html` 22:09 有改动
- `dist/` 22:13 重建
- `build/dist-site.zip` 22:16 重打
- 线上 `https://auxiaweb.pages.dev/` 返回 **HTTP 200 / 11655 字节**，与本机 `dist/index.html` **md5 完全一致**
  （`c8c7601c44ef4e514d844b2e940f69eb`）

也就是说：**改一版 → 构建 → 打包 → 上传 → 线上生效，走了约 7 分钟。**
（这条推断的前提是"你自己传了一次"；如果不是你传的，请告诉我，那说明还有别的自动化在动这个项目。）

结论：**慢的从来不是发布，是"想清楚要改什么"和"证明改对了"。**
流程一旦被固化成一串确定命令，它就是分钟级的。

### 1.4 悬而未决的小决策，会一直挂在每轮尾巴上

- **"部署"这件事连挂了 4 轮**：第一、二、三、四轮的"仍未做"里都有它，理由是"用户选了先出完整成品再部署"。
  代价在第五轮集中兑现：上线时才发现 `file://` 打开是坏的、`_headers` 在内置通道不生效、Cloudflare 卡在登录。
- **`banner.lines` 里 3 条占位文案连挂 3 轮**（第二、三、四轮"仍未做"），到第六轮才一并处理。
- **正式域名到第六轮才定**，而 `canonical`/`og:*` 是从 `PUBLIC_ORIGIN` 派生的 —— 于是换域名那天要动
  `build_icons.py → gen_project_pages.py → build_fonts.py → build_site.py` 一整条链，还暴露出"域名写死在手写页面里"的老坑。

**这三个都不是"AI 慢"，是"决策延迟"在按轮计息。**

## 2. 把"2 小时"拆开看

日志里的时间大致落在四类：

| 类别 | 说明 | 是否可省 |
|---|---|---|
| **A 需求探索** | 用户给需求、AI 复述、边界靠实现时才发现 | 部分可省（靠流程，见 §4） |
| **B 真实难度** | 一言 85% 背后的四环算术（需求/预算/并发/CF 缓存）、弹幕 12% 高亮失效、多层 CSS 继承 | **不可省**，只能靠实测 |
| **C 验收成本** | 259 条自检、真机浏览器探针、逐项 curl、注入故障验红 | 可分级压缩（见 §5.3） |
| **D 过程成本** | 环境坑、测量工具本身错、自我假绿、生成物覆盖、误操作 | **本该为 0** |

D 类的证据（全部出自日志原文，均为"不产生产品价值"的耗时）：

1. `cd X && cmd &` 把 `cd` 丢进后台子壳 → 报错伪装成 `MODULE_NOT_FOUND`（`2026-10-01.md:451`）
2. 前台跑超 20 秒的探针被 SIGTERM（`:454`）
3. `tasklist | grep -ci msedge` 把宿主的 `msedgewebview2.exe` 也数进去（`:457`）
4. `fault-inject.sh` 第一版跑出 **11/11「守卫没抓到」**，其实是脚本自己假绿，一个变异都没注入（`:461`）
5. 守卫"假绿"三连：拿整份文件搜 `backdrop-filter` 被别的规则喂绿 → 正则撞上 `-webkit-` 前缀 → 第三次才有牙（`:262-269`）
6. `formulaErr 3212` —— 测量公式本身写错，把**完全正确**的代码误判成错，差点去改它（`:149`、`:167`）
7. `expectedLive 75` vs 实测 43 —— 探针的理论公式又错了一次，制造出"密度 bug"的假象（`:439-442`）
8. jsdom 的 `requestInterceptor` 看不到 `file:` → harness 整条重做，此前 404 页 JS 从没执行过（`:88-92`）
9. 截图时序陷阱：第一轮写下教训，**第二轮复发**，第三轮才把它做成 `&slow=` 探针参数（`:41-46`、`:101-102`、`:178-183`）
10. 文件夹上传挂死 2 分多钟（`2026-10-02.md:27-29`）
11. 打包脚本误操作压出 2.9GB 的包（`2026-10-02.md:33`）

第 9 条是整份材料里最值钱的一条教训：

> **把教训写进 README，不等于修好了它。** 第一轮就写下"headless 截图会骗人"，
> 第二轮照样复发。它是在被做成**工具默认路径**（`preview.py` 的 `&slow=` 参数）之后才真正不再复发的。

## 3. 对你三条发现的回应

### 3.1 "一开始就要有大致构想，而且要先讨论" —— 对，但落点不是讨论更久

你已经讨论了，问题在于**讨论没有产物**。现在缺的不是时间，是一份**能被验收的 SPEC**。
判据很直接：如果当初有一份写着验收标准的 SPEC，"部署"不会挂 4 轮、"域名"不会到第六轮才定。

"细化"不等于把话说得更漂亮，而是把每条需求翻译成**一句可验证的话**：
> "弹幕里 85% 来自一言" → 判据：刷新页面 30 秒后，`hkShare ≥ 0.8` 且 `hkMiss ≤ 2`。

说不清的，就明确写进"本轮不做"。说不清还硬做的，最后都会变成修补。

### 3.2 "是不是思考模式和深度出了问题" —— 深度没问题，方向错了

这次真正难的几处（一言四环、静默吞非 200、`fill-mode` 压掉 `:hover`）都挖到了底，
说明深度是够的。问题在于**深挖发生得太早**：

- 第六轮：改完 `ratio` 实测 0.33，于是开始逐环深挖 —— 这时候连"85% 由哪些环决定"都还没写下来过。
- 第三轮：`formulaErr 3212`，差点去改一段**本来正确**的代码 —— 深挖发生在"确认它到底坏没坏"之前。

**该省的不是深度，是深度投入的时机。** 先"用真实数据确认现象"，再决定要不要深挖。

### 3.3 "AI 是不是在做无用功" —— 是，但分三类，各有解药

| 类别 | 典型表现 | 解药 |
|---|---|---|
| 环境型浪费 | 进程被 SIGTERM、`cd` 丢进子壳、数错进程、输出被吞 | 固定"已知路径 + 已知红线"清单，5 分钟止损（§5.5） |
| 验证型浪费 | 守卫假绿、度量公式自己写错、把正确代码判成错 | **度量工具本身必须有正/负样例**，否则它的结论不可信（§5.4） |
| 返工型浪费 | 需求漂移、生成物覆盖手改、隐式顺序依赖（`gen_project_pages` → `build_fonts`） | SPEC 冻结 + 单一真源 + 生成物头部标注"勿手改"（§5.1） |

而"真实难度型"的耗时（四环算术、12% 高亮）**不是无用功** —— 那类只能靠实测，
省它的唯一办法是不做这个需求。

## 4. 与成熟范式、以及你已装的 skill 对照

| 环节 | 成熟范式 | 本次实际 | 你本地已装的对应 skill |
|---|---|---|---|
| 意图探索 | 先问清"怎么算成功" | 直接开做，边界在实现中浮现 | `brainstorming` |
| 规格 | 冻结 + 写死验收标准 | 口头需求，无 SPEC 文件 | `writing-plans` |
| 执行 | 小步，每步都可上线 | 大轮，末尾统一验收 | `executing-plans` |
| 验证 | 先验证度量本身 | 度量错了才发现 | `verification-before-completion` |
| 排障 | 先确认现象再改 | 有一次差点改对代码 | `systematic-debugging` |
| 并行 | 独立任务并行分发 | 全程串行 | `dispatching-parallel-agents` |

**最扎心的一条**：这套流程你本地已经装好了，这次一项都没被系统性调用。
所以"下次提升效率"的抓手不是学新东西，而是**在开轮之前强制走一道这几个 skill 的入口**。

**最具体的一条**：第六轮那 9 项主任务里，至少 5 项彼此独立
（SC3 接入 / 新 favicon / 标题休眠 / 点击弹幕搜 Bing / 开屏页），完全可以并行分发，
实际却是串行做完的。一轮 2 小时里有相当一部分是"本可以并行的时间被串行花掉了"。

## 5. 下一次怎么做

### 5.1 启动阶段：30-40 分钟，不碰代码

产出两个文件（用 `writing-plans` 生成），放在项目根：

1. `SPEC.md`
   - 一句话目标
   - **成功判据**：每一条都要能回答"谁来验、怎么验、看到什么算过"
   - **本轮不做**：显式列出被砍掉的（含所有还说不清的）
   - 已知约束：域名、宿主、依赖、不能动的东西
2. `PLAN.md`
   - 按"可上线的垂直切片"排序，**每个切片结束都要能发一次**
   - 标出哪些切片彼此独立（可并行）

另外：**先做一条最窄的端到端**（内容 → 页面 → 上线），哪怕丑。
把"上线"放到第 5 轮才做，代价在第五轮一次性付清了。

### 5.2 每轮的节奏：把"轮"变小

- 一轮 ≤ 60-75 分钟，**只放一个主题，最多 3 项任务**；9 项任务拆成 3 轮。
- 固定三段：实现 ≤40 分钟 / 验收 ≤15 分钟 / 收尾 ≤10 分钟（更新文档、记忆、打包）。
- 三条硬规则：
  1. **5 分钟止损**：卡在环境或工具上超过 5 分钟，先记一条，改用已知路径，别继续试。
  2. **改完就 `build_site.py` + 自检**（自检读的是 `dist/`，不重建等于在测旧构建）。
  3. **轮末必须更新线上** —— 哪怕只改了一行。这直接消灭"先出完整成品再部署"这类延迟上岸。

### 5.3 验收分级（本次最省时间的杠杆）

| 级别 | 内容 | 什么时候跑 |
|---|---|---|
| L0 | `build_site.py`（构建 + 占位符残留检查） | 任何改动 |
| L1 | `smoke-test.cjs` 259 条 | 任何改动 |
| L2 | 真实浏览器探针（几何、动画、材质、指针向量） | 只改布局/动画/材质/交互时 |
| L3 | 线上 `curl` + 关键路径逐项 | 只在轮末 |

改纯文案、颜色、数据 → 只跑 L0+L1。
改 JS 行为 → 加 L2。改架构/域名 → 全套。
**不要每次改动都跑 L2** —— 那是当前最贵的一项，也是最常被无条件跑的一项。

### 5.4 三条防"无用功"机制

1. **改代码前，先用真实数据确认现象**（这条第一轮就有，是本次最有价值的习惯，升级为铁律）。
   它已经证明过一次价值：省掉一整轮"照着不存在的问题改代码"。
2. **度量工具自己要有样例**：每个新的探针/断言，都要能对一个人为构造的**正例**和一个**负例**给出不同结论。
   做不到，就说不出"没问题"三个字。（本次 5 次"假绿"全部来自这一步的缺失。）
3. **教训要变成默认值，不是文档里的一段话**。判据：如果这条教训不能变成脚本参数、守卫或一行默认命令，
   那它下次一定会复发（截图时序陷阱的复发就是证明）。

### 5.5 两张可复用的止损清单

**已知路径（直接用，不要试探）**

> 本机绝对路径不在本文档里（这个是公开仓库）。真源是工作区记忆
> `.workbuddy/memory/MEMORY.md`，以及 `tools/local.json`。

```bash
cd <项目目录>/auxia-site
PY=$(command -v python)          # 本机真源见 MEMORY.md
NODE=$(command -v node)

$PY tools/build_site.py                                  # L0
AUXIA_NODE_PATH=<jsdom 所在目录> $NODE tools/smoke-test.cjs   # L1
$PY tools/preview.py                                     # 看网站，唯一正确方式（别双击 html）
$PY tools/make_dist_zip.py                               # -> build/dist-site.zip
```

**已知环境红线（踩了就换路，别重试）**

- 前台跑 >20 秒的探针会被 SIGTERM → 后台跑 + 落盘，**先读文件再决定要不要重跑**
- 留下活着的浏览器进程会被整条命令带走 → 用 `preview.py` 的探针参数，不常驻 CDP
- 从 Bash 里执行名字里带特定关键词的命令会被安全策略拦 → 改用对应工具本体
- 输出被吞时：写文件再读，不要反复重跑同一条命令
- 构建脚本输出**不要接 `head`/`tail`**（SIGPIPE 会静默把 `dist/` 搞成半成品）

## 7. 本次其实做对了、不要因为"慢"丢掉的部分

- **把教训变成守卫，并且每条都注入故障验红** —— 这是 259 条自检能立住的原因。
- **度量优先于改动**：先量再改，避免了两轮"照着不存在的问题改代码"。
- **单一真源**：域名、色板、数据各自的唯一来源，并且发现"改一处全站同步"是假的时候立刻做了真源。
- **发布流程固化后是分钟级的**（§1.3 实测约 7 分钟）。

这些是"正确答案 + 慢"，不是"错答案 + 快"。优化目标是砍掉 D 类（过程成本）和串行浪费，
**不是砍掉验收**。

## 8. 需要你回答的两件事（只能你知道）

1. **一轮 2 小时里，有多少是你在等 AI 跑、盯着屏幕的时间？**
   如果占比高，那优化方向不是"让 AI 想得更快"，而是把所有长任务改成后台执行 + 完成后通知。
2. **你更看重"一次做对"还是"尽快看到能用的东西"？**
   这决定 L2 验收是否要默认关闭、以及第一轮的"最窄端到端"要多窄。
